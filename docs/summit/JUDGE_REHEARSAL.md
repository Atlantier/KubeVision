# R54 · 评委视角彩排（JUDGE REHEARSAL）

> 目的：把「技术 / 产品 / 投资」三类评委的刁钻追问 + **追问链**提前打穿；
> 每题限时 **40 秒**，按 **证据（0–2）/ 诚实（0–2）/ 40 秒内（0–2）** 三项打分（满分 6）。
> 两轮：R1 暴露问题 → 修正 → R2 复测。第三轮随机抽 6 题验收。
> 所有答案只引用仓库可核对的事实；**没有实测的数字不许说**。

---

## 1. 评分口径（每个评委独立打）

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 证据 | 只有结论，无文件/数字 | 有数字但记不清出处 | 当场能给出文件路径 + 最新数字 |
| 诚实 | 把未验证说成已验证 | 承认边界但含糊 | 明确说"未验证/不能宣称"，并给替代证据 |
| 40 秒内 | >50s 或被打断 | 40–50s | ≤40s 且结构完整（结论→证据→边界） |

**答题模板**：`结论（1 句）→ 证据（文件+数字，1–2 句）→ 边界（1 句）`。

## 2. 技术评委（T1–T5）

### T1「你们的'三路召回'生产上真的可用吗？」
**追问链**：证据？→ 端侧 Worker 失败/断网怎么办？→ 评测是不是自说自话？

- R1（弱，3/6）：「已经上线了，三路召回效果很好。」（无文件、未验证当已验证）
- R2（好，6/6）：
  「**不能说生产已上线**。引擎支持 384 维查询向量、Worker embed 协议和 `/api/chat` 入参都做了，但浏览器端到端未真机验证；端侧不可用时自动两路。证据：`docs/summit/R45-worker-embed-production.md`、`docs/rag-eval.md`（49 用例，两路 R@1 88.9%→三路 94.4%，+5.6pp，两次运行一致）。边界：那 49 条是构造用例，不是线上流量。」

### T2「60FPS 是真的吗？性能数据凭什么？」
**追问链**：draw calls 怎么来的？→ 软渲染能代表真机？→ 真实 GPU 数据有吗？

- R1（弱，3/6）：「我们优化得很好，基本 60 帧。」（无实测）
- R2（好，6/6）：
  「**不能宣称 60FPS**。本机只有 SwiftShader，实测中位 FPS 5（均值 4.75），所以答辩只讲硬件无关指标：`docs/performance.json`（2026-11-14 重采）draw calls median 235（20 次采样 235~238）、154 mesh、27 个 InstancedMesh 承载 1,017 实例、206,626 三角面。边界：真实 GPU 数据没有，白皮书 8.5 已写明『无 GPU 环境声称 60FPS 不诚实』。」

### T3「MCP 是标准实现吗？能和官方 SDK 互通吗？」
**追问链**：transport 是什么？→ 有没有做握手测试？→ HITL 在哪一层？

- R1（弱，2/6）：「完全标准 MCP。」（过度承诺）
- R2（好，6/6）：
  「是 **JSON-RPC 2.0 over HTTP**：`/api/mcp` 支持 initialize / tools/list / tools/call / ping，错误码按规范；**不是 stdio transport**，所以不能直接说与官方 CLI 全互通——只做了 `scripts/mcp-smoke.mjs` 10/10 的自测。HITL 在执行层：写操作必须 `/api/mcp/execute` + 用户确认，模型不能直接执行。证据：`src/app/api/mcp/route.ts`。」

### T4「RAG 评测是不是自说自话？三路只涨 2.8pp 有意义吗？」
**追问链**：用例谁写的？→ 关键词正确率 vs Recall 区别？→ 统计显著性？

- R1（弱，4/6）：「涨了就是有提升。」（无口径）
- R2（好，6/6）：
  「评测是**自建 49 条**（12 篇手册机械派生口语/错字/混杂 36 条 + 8 负例 + 5 多文档），脚本 `pnpm eval:rag` 可复现，两次结果一致。三路 R@1 88.9%→94.4%（+5.6pp）、NDCG@5 0.918→0.979；**没有做显著性检验**，5.6pp 只能说明在这批用例上排序变好，不能外推。负例拒答 100%、误拒 0%。边界：用例构造化，不是线上分布。」

### T5「多步工具、grounding 真跑过吗？怎么防模型胡说？」
**追问链**：哪些未验证？→ `[未证实]` 标注怎么触发？→ 证据不足怎么钳制？

- R1（弱，3/6）：「都实现了，效果不错。」
- R2（好，6/6）：
  「**多步只读工具在评测时没被模型实际调用**（当时 LLM 持续回落 simulate），这条未验证，文档里写了。grounding 已生效：引擎 B 报告里找不到出处的实体/百分比标 `[未证实]`；根因卡置信度按证据强度钳制（观测+RAG=0.92，仅其一=0.6，都没有=0.4）。证据：`src/utils/grounding.ts`、`docs/summit/R47-grounding.md`（实测空观测流里出现 `[未证实]` 与汇总）。」

## 3. 产品评委（P1–P5）

### P1「谁会用？什么时候用？和告警平台/kubectl 什么关系？」
- R1（弱，4/6）：「所有 K8s 用户都能用。」
- R2（好，6/6）：
  「定位是**告警之后、kubectl 之前的 5 分钟**：值班人先看懂空间关系与根因，再决定动作。不是替代告警平台，也不是替代 kubectl，是承接"看懂了再动手"。证据：`docs/summit/DEMO_DIRECTOR_PLAYBOOK.md` 的演示动线就是告警→定位→RAG→自愈→复盘。边界：目前没有真实客户使用数据。」

### P2「为什么一定要 3D？会不会增加认知负担？投影/色弱怎么办？」
- R1（弱，3/6）：「3D 更酷，评委喜欢。」
- R2（好，6/6）：
  「3D 只承担一件事：**空间索引**——点 Pod 就飞过去，点卡片能反查 3D；表格仍在，探针卡给的是真实指标。认知负担用两条兜底：所有信息都有文本卡片，颜色不是唯一编码（文字+图标），并支持演示模式放大字号。边界：没有做正式可用性测试，色弱适配只做到"非颜色单通道"。」

### P3「离线优先和 SaaS 商业化不矛盾吗？模型怎么更新？」
- R1（弱，3/6）：「我们既离线又 SaaS，都行。」
- R2（好，5/6）：
  「离线优先是**演示与信创场景的卖点**，SaaS 是另一条线：私有化部署卖授权，云端卖订阅。模型/手册更新靠版本包与策略下发，不依赖现场网络。矛盾点在于离线版本的模型更新会滞后——这是有意取舍。证据：`docs/COMPETITION_TECHNICAL_WHITEPAPER.md` 第七章数据边界、`public/models/README.md`。边界：没有真实付费客户验证。」

### P4「上手成本多高？需要什么权限？失败怎么退出？」
- R1（弱，3/6）：「开箱即用。」
- R2（好，6/6）：
  「演示态零依赖：`pnpm build && pnpm start`，不需要真实集群、不需要外网 Key；接真实集群才需要只读 K8s 权限。失败退出：引擎 B 兜底、高危动作必须人工确认、执行有回执。证据：README 快速开始；双机预案 `docs/summit/DUAL_MACHINE_CHECKLIST.md`。」

### P5「和 Grafana / Lens / KubeSphere 的差异？他们加 AI 你们怎么办？」
- R1（弱，3/6）：「我们更 AI。」
- R2（好，5/6）：
  「差异不在图表，在**把空间、检索、执行、复盘串成一条闭环**，且离线可跑（端侧模型+确定性引擎）。大厂加 AI 是必然，我们的生存点是垂直场景的离线/信创交付与"人类在环"的执行审计。边界：这是判断，不是已验证的竞争结论。」

## 4. 投资评委（I1–I5）

### I1「市场多大？怎么收钱？有营收吗？」
- R1（弱，2/6）：「市场很大，K8s 都在用。」（无结构）
- R2（好，5/6）：
  「**没有营收数据，只有成本结构与假设**：按集群数订阅 + 私有化授权是两条线；目标客户是没有专职 SRE 的中小企业。市场论证需要第三方报告，本次没有引用，避免编数字。证据：README 商业模式一节。边界：无客户、无付费验证。」

### I2「护城河是什么？3D 不是谁都能做吗？」
- R1（弱，2/6）：「3D 很难做。」
- R2（好，5/6）：
  「3D 本身可抄；可积累的是三样：**离线端侧链路**（脱敏+模型+确定性引擎）、**运维语义资产**（RAG 手册/评测集/审计回执格式）、**演示到交付的工程化**（verify/证据/双机/录屏）。边界：这些是工程资产，不是专利壁垒。」

### I3「单位经济模型？每次 LLM 调用多少钱？」
- R1（弱，2/6）：「很便宜。」
- R2（好，5/6）：
  「成本按 env 单价计算：`KV_PRICE_INPUT_CNY_PER_MTOK` / `KV_PRICE_OUTPUT_CNY_PER_MTOK`，未配置时 trace 里显示『未配置』而不是编一个数。当前 20 问评测平均 prompt 9,180 / completion 3,250 tokens（RAG 路径），可据此换算单次成本。边界：没有真实账单数据，单价随供应商波动。」

### I4「团队/交付风险？就这点人怎么持续？」
- R1（弱，2/6）：「我们效率很高。」
- R2（好，5/6）：
  「单点风险真实存在：代码/文档/演示集中在一人。缓解是把**验证与演示都脚本化**（verify 33/33、eval 脚本、打包脚本、录屏手册、双机预案），让接手者能按文档复现。边界：没有第二维护者，这是风险不是优势。」

### I5「如果云厂商把同类能力集成进控制台，你怎么办？」
- R1（弱，2/6）：「他们做不了。」
- R2（好，5/6）：
  「云厂商会覆盖"在线 SaaS"场景；我们守两条：**离线/信创内网**与**演示—交付一体化**。若被集成，最坏结果是成为其插件/被收购。边界：这是策略判断，没有市场验证。」

## 6. 第三轮（验收）执行方法

- 从 15 题中**随机抽 6 题**（技术 2 / 产品 2 / 投资 2），每题 40 秒；
- 评委可连续追问 2 层；主讲若超时/被问住，立即用模板收口：
  「这条我明确是未验证/无数据，对应的证据/边界在 `<文件>`；我可以在会后补跑脚本给您。」
- 通过线：**≥ 5.0 / 6 平均**，且三个维度均不低于 1 分；
- 记录表：

| 题号 | 结论 | 证据 | 诚实 | 40s | 追问是否接住 | 改进 |
|---|---|---|---|---|---|---|
| | | /2 | /2 | /2 | 是/否 | |

**彩排节奏建议**：R1 与 R2 间隔 ≥24h；R3 在正式答辩前 2 天；每次彩排录音，回听自己有没有出现禁语（60FPS/真实集群/标准 MCP/1 秒回落/准确率 X%）。
